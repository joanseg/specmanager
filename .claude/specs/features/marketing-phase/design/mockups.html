### Channels
- …
  • Searches = avgMonthlySearches12, copied as-is (no separators, no rounding); null prints —, never 0.
  • Competition = LEVEL (index); a null index prints (—).
  • Trend = arrow + trend.verdict + trend.pctChange signed to one decimal. Arrows: ↑ increasing, → stable, ↓ decreasing, · insufficient_data. A null pct prints (from zero) for increasing and nothing for insufficient_data. Arrows carry the meaning because Markdown cells can't be coloured.
  • Source line right under the table uses the resolved region and language, not the user's input, and ends with trend.rule verbatim.
  • The close-variants and unmatched lines are printed only when they are non-empty.
  • Year-over-year cancels seasonality, so the v1 seasonality caveat is gone. insufficient_data explains itself through the rule text (floor 50/mo).

Screen 3 — one line instead of the table

### Demand
> Demand data unavailable — <reason, or missing-settings summary>
  • Exactly one line (R2), as a blockquote so it reads as a note rather than as body prose. It uses neutral grey, not an error colour: missing access is an expected, opt-in state. The ### Demand heading stays, so the outline is the same whether or not data came back.
  • Unavailable: the missing key names only (never values). Only four are listed, because login_customer_id isn't required. The line mentions Basic access, since that is the first thing users hit.
  • Error: the tool's reason verbatim (R7 explain() table). A request id is appended only when Google returned one; token errors have none. The error code is in the mock for traceability, but only if the reason string carries it (see Open questions).
  • No table, source line or channels are invented from the missing data. The PRD is still written.

Screen 5 — command output

The command is Markdown the main session writes and Claude Code renders, so only content and order are binding (R12):

  • ok: one heading line (resolved region + code, language, API version), then the same four-column table as the PRD so users learn one format. Then close variants and unmatched when non-empty, and a dim footer with trend.rule, fetchedAt and “nothing written”.
  • unavailable: framed as “isn't set up” and “optional”, not as a failure. It lists the missing key names, then five steps in the order that avoids dead ends: Basic access first (the most common blocker), OAuth client, consent screen to Production plus refresh token, customer id, where to enter the values. It says explicitly that no developer token is needed.
  • error: the reason verbatim, then the request id if there is one. No stack trace, no retry loop.
  • Missing --region: ask once and stop, with no tool call (not mocked; one line).

Screen 6 — the optional settings

This is an approximate mock: Claude Code owns this UI, and only the manifest strings are ours (R5). What the builder controls:

  • Titles end with (optional — keyword demand only), exactly as shown, so someone skimming install prompts can skip them with confidence.
  • Descriptions carry the one setup fact each field needs (Basic-access project, Production consent screen, manager account). They stay under about 60 characters.
  • The three secrets are sensitive: true, so they are masked and kept in the OS credential store. The two customer ids are not sensitive, so they can be edited later in /config.
  • All five are default: "" and not required, which is why the default state is “not set” with no warning.

Open questions for the planner

  1. Error code in PRD fallback lines. R7's reason strings don't include the Google code (for example CLOUD_PROJECT_NOT_APPROVED_FOR_PRODUCTION); Screen 3 shows it appended for traceability. Either have explain() append code when present, or drop it from the line. Recommended: append it, because it makes support searches trivial.
  2. Where the five fields actually appear. Architecture Q2 (prompting on install and update) is unverified, and sensitive fields may not be listed in /config at all. Screen 6 is the plugin-configure view. The manual check the plan must include should also confirm that the titles render there.
  3. Right-aligned numbers (--:): verify that Milkdown keeps column alignment on round-trip and that it overrides .markdown td { text-align: left }. If not, leave the numbers left-aligned; don't add CSS for it.
  4. No thousands separators is the literal “verbatim” reading. If separators are wanted, the prd-writer rule and selftest-prompts must say so explicitly.
  5. No tokens added and no board or UI code changes. docs/DESIGN.md's managed frontmatter is still thin; tokens.css remains the real source.
