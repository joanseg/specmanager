The loop

Seven stages. Claude drafts each one — you approve before the next unlocks.

Copy a command, review what Claude wrote in the board, approve. That approval is the gate that opens the next stage. Interview and Design are optional; the other five are the spine.

1

Interview optional

Talk the idea out first. A forcing-question interview pulls the feature out of your head and stress-tests it before any spec exists.

you approve: nothing — it just leaves an interview.md the PRD reads. Gates nothing.

/specmanager:specmanager-interview⧉ Copy
2

PRD

Pin down the problem. The product manager drafts users, jobs-to-be-done, goals and success metrics — the thing worth building.

you approve: prd.md → unlocks Architecture & Design.

/specmanager:specmanager-prd "Checkout corridor"⧉ Copy
3

Architecture

Fit it to your codebase. The architect reads your real repo — structure, conventions, what's already there — then specs how the feature lands.

you approve: architecture.md → unlocks Plan.

/specmanager:specmanager-architecture <feature>⧉ Copy
4

Design optional

See it before you build it. The designer produces high-fidelity HTML mockups grounded in your design system, with a live preview in the board.

you approve: the mockups → if one exists, Plan waits on it too.

/specmanager:specmanager-design <feature>⧉ Copy
5

Plan

Break it into shippable pieces. The tech lead splits the work into phases and small, Fibonacci-scored tasks — defaulting to the smallest increment that ships.

you approve: plan.md + tasks → unlocks Build.

/specmanager:specmanager-plan <feature>⧉ Copy
6

Build

Ship it, one phase at a time. The builder works each task in order and stops at the phase boundary; a read-only reviewer checks the phase against the spec.

you approve: nothing to sign — the phase is done when every task is done.

/specmanager:specmanager-build <feature> next⧉ Copy
7

Walkthrough

Write down what shipped. The tech writer documents each finished phase, then a final roll-up once every phase walkthrough is approved.

you approve: the walkthrough doc → approving the final one ships the feature.

/specmanager:specmanager-walkthrough <feature> <phase>⧉ Copy
Claude drafts → you review & approve in the board → next stage unlocks · the gate is enforced in code, not a prompt Claude can talk its way around.

📄 README.md Preview · rendered markdown

SpecManager

Your AI agile team, as a Claude Code plugin. From vibe coding to spec'ing and shipping production-ready features.

You already have the builder — Claude Code. What you don't have is the rest of the squad: the PM who pins down the problem, the architect who fits it to your codebase, the planner who cuts it into shippable pieces, the reviewer who checks the work against the plan. SpecManager is that team — a set of specialised agents that draft, while you review, edit and approve. Spec-driven development you can actually see: a local kanban board, one row per feature, one column per stage.

Don't have Claude Code? Get it in 2 minutes → code.claude.com/docs/en/quickstart

specmanager.org · MIT licensed · runs entirely on your machine — single-user, local, no login.

Existing / multi-repo workspace (meta-repo mode): point init at your sibling repos —

/specmanager:specmanager-init /path-to/repo-1 /path-to/repo-2

A workspace folder holds your sibling git repos; one meta repo runs SpecManager and orchestrates changes across them. Siblings passed to init are read-only — SpecManager never writes outside the meta root.

Requirements: Node 20+, Claude Code, a git repo. No build step — the compiled server and UI ship in the plugin; a SessionStart hook installs runtime deps on first launch. The board runs at http://127.0.0.1:4317.

The workflow — seven stages, zero to shipped

Each feature is a row that flows left to right. You drive it with slash commands; Claude drafts via dedicated subagents; you approve each stage in the board before the next unlocks — the gate is enforced in code, not in a prompt Claude can talk around. Interview and Design are optional; the other five are the spine.

StageCommandYou approve
Interview (optional)/specmanager:specmanager-interviewnothing — leaves interview.md for the PRD

assets/board-shipping.png — the board with Build 28/28 and an approved Walkthrough

"Approved" is a commitment, not a freeze. Reopen an earlier doc and every doc that depended on it gets a non-blocking stale badge that follows the dependency chain. And because edits are tracked with optimistic concurrency, a late agent write can never clobber a change you made by hand.

Where your work lives

Everything is markdown with YAML frontmatter, under your project, version-controlled by git.

# single repo
<your-project>/
  CLAUDE.md                  # managed SpecManager block (between markers)
  docs/DESIGN.md             # managed design-system spec
  .claude/specs/
    manifest.json            # rebuildable board index (from frontmatter)
    features/<slug>/
      feature.json
      prd/ architecture/ design/ plan/ walkthroughs/

# meta-repo (orchestrates read-only siblings)
<meta-repo>/  .claude/specs/ …   <sibling-backend>/   <sibling-frontend>/

Frontmatter is authoritative; manifest.json is a cache you can delete and rebuild. Managed regions in CLAUDE.md/DESIGN.md live strictly between <!-- specmanager:start --> / <!-- specmanager:end --> — nothing outside them is touched.

Contributing / building from source

The plugin ships compiled server/dist and ui/dist, so users install with no build step. Rebuild before committing source changes:

cd plugins/specmanager/server
npm install && npm run build
npm run selftest          # core flow
npm run selftest-board    # REST + WS + watcher
cd ../ui && npm install && npm run build

Tech stack: Node 20+, TypeScript, MCP stdio, Fastify + ws, chokidar, gray-matter, zod, React 18 + Vite, CodeMirror 6. One shared @specmanager/core backs both the MCP server and the board server; one MCP process boots the board.

Troubleshooting

  • /mcp shows specmanager failed — select it and reconnect; if it persists, fully quit Claude and relaunch from your project.
  • Board won't open — the MCP process boots it on startup; restart your session. /specmanager:specmanager-board reports the URL.
