> Based on PRD `prd-viral-loop-feature-022` (v2, approved). No design doc exists for this feature. The PRD's answered open questions are treated as settled: the designer emits a second, navigation-aware artifact; published URLs are unguessable with an unpublish action; the user owns the hosting account; design changes require shipping a new URL; the visit→install attribution gap is accepted.

## 1. Summary

We add an optional **Prototype** artifact to the design stage. It is a second self-contained HTML document per feature — generated by a designer-style agent from the existing `design/mockups.html` plus the PRD's flows — with client-side navigation wired between screens. It surfaces on the board as a chip stacked under the design card (exactly the pattern the Interview chip uses under the PRD card); clicking the chip opens the prototype full-page in a new browser tab, served raw by the existing board server. Phase 1 is entirely local. Phase 2 adds a host-agnostic `core/publish.ts` that deploys the prototype to an unguessable public URL on a Netlify-class static host (user-owned account, token outside the repo), injecting a "built with ❤️ specmanager.org" footer badge with UTM params at publish time. The prototype is a non-lifecycle artifact: like the interview, it is excluded from gating, stage labels, and primary-card selection, and its staleness rides the existing `dependsOn` graph.

## 3. Data model changes

No new files-on-disk format, no migration. One enum value and (phase 2) three optional frontmatter fields.

```
.claude/specs/features/<slug>/design/
  mockups.html      # existing design brief (unchanged)
  prototype.html    # NEW — kind: "prototype", self-contained clickable flow
```

Prototype frontmatter (phase 1):

- `stage: "design"`, `kind: "prototype"`, `status: "draft"` **frozen by convention**, exactly like the interview — nothing reads its status, nothing gates on it, no UI approve affordance.
- `dependsOn: [<design doc id>]`, `basedOn: { <design doc id>: <version> }` (commonly also the PRD id). This is the whole staleness story: reopening the approved design (`approved→draft`) hits `propagateStale` in `core/status.ts` (line 42) and flags the prototype stale — zero new staleness code.

Phase 2 additions to `DocFrontmatterSchema` (all optional, only ever set on `kind: "prototype"` docs):

```ts
publishedUrl: z.string().optional(),       // public URL, or absent = not published
publishedAt: z.string().optional(),
publishedVersion: z.number().int().optional(),  // doc version at publish time
```

A public URL is not a secret, so committing it in frontmatter is fine and keeps frontmatter authoritative (deleting `manifest.json` loses nothing). `publishedVersion !== version` ⇒ the public URL shows an outdated prototype ("new URL needs to be shipped" per the PRD).

## 4. Interfaces

**Core (`server/src/core/documents.ts`)** — no new function; `createDocument` gains one validation branch:

```ts
if (input.kind === "prototype" && input.stage !== "design") {
  throw new Error(`kind "prototype" requires stage "design" (got "${input.stage}")`);
}
```

**MCP (`server/src/mcp.ts`):**

```ts
create_prototype({
  featureId: string,
  title: string,            // "<Feature title> prototype"
  body: string,             // one self-contained HTML doc, ≤ 5MB
  dependsOn?: string[],     // [designDocId, prdId]
  basedOn?: Record<string, number>,
}) // → docAck; writes design/prototype.html, status draft, generatedBy agent
```

**Board server (`server/src/board-server.ts`):**

```ts
app.get<{ Params: { id: string } }>("/api/documents/:id/raw", ...)
// 200 text/html with doc.body iff filePath ends in .html; 404 otherwise.
// 127.0.0.1-only like everything else; no auth, consistent with the board.
```

**Publish contract (`server/src/core/publish.ts`, phase 2)** — deliberately artifact-agnostic so `feat-share-docs-on-public-url` can ride it later:

```ts
export interface PublishInput {
  files: Array<{ path: string; content: string }>; // prototype = [{ path: "index.html", ... }]
  label: string;                                   // e.g. feature slug, for host-side bookkeeping
}
export interface PublishResult { url: string; siteId: string; }

export async function publish(input: PublishInput, root?: string): Promise<PublishResult>;
export async function unpublish(siteId: string, root?: string): Promise<void>;
```

Notes on the contract:

- **Nothing prototype-specific.** `publish_prototype` composes: read prototype body → inject badge footer (`<a href="https://specmanager.org?utm_source=prototype&utm_medium=badge&utm_campaign=viral-loop">built with ❤️ specmanager.org</a>`) → `publish()` → stamp `publishedUrl/At/Version` via the normal frontmatter write path. The badge lives in the *published* copy only; the local artifact stays clean.
- **Unguessable URL:** the host site name is minted with a random suffix (e.g. `sm-<slug>-<random12>.netlify.app`). Re-publish after a design change mints a **new** site and unpublishes the old one (PRD: "new URL needs to be shipped"), so a stale URL can't linger by accident.
- **Secrets:** host token read from `SPECMANAGER_PUBLISH_TOKEN` env or `${CLAUDE_PLUGIN_DATA}/publish.json` — the same out-of-repo persistence pattern the SessionStart hook already uses for `node_modules`. Never written under the project root, never in frontmatter. Missing token ⇒ actionable error naming both locations.
- **Consent:** publish is never a side effect. The board shows an explicit confirm dialog ("this becomes publicly reachable"); the MCP tool requires `confirm: true` and the `/specmanager-prototype` command instructs the agent to ask the human first.

## 5. Sequence / flow

**Generate (phase 1):** `/specmanager-prototype` → delegates to `agents/prototyper.md` → agent reads the approved PRD, `design/mockups.html` (via `read_document`), and `docs/DESIGN.md` tokens → emits one self-contained HTML doc where each screen is a full-viewport section and click targets navigate between screens (hash-based `:target` sections or a tiny inline script — no external deps, works offline and from `file://`-grade hosting) → persists via `create_prototype` → `createDocument` writes `design/prototype.html`, emits `document.created`, manifest rebuilds → chokidar/WS pushes → chip appears under the design card.

**View (phase 1):** chip click → `window.open("/api/documents/<id>/raw")` → Fastify reads the doc via `readDocumentById`, returns body as `text/html` → full-page clickable flow in a new tab. (The existing `DocPanel` sandboxed-iframe preview still works if the doc is opened as a doc; the chip's new-tab path is primary per the PRD.)

**Design change:** human reopens the design (`approved→draft`) → `propagateStale` flags the prototype → chip shows the standard stale badge → user re-runs `/specmanager-prototype`, which updates the doc in place via `write_document` + `baseVersion` (the interview re-run pattern), bumping `version`.

**Publish (phase 2):** user clicks Publish on the chip (or asks Claude) → consent confirm → `publish_prototype` injects badge, calls `core/publish.publish()` → frontmatter stamped with `publishedUrl/At/Version` → `document.updated` event → UI shows the public link + Unpublish. Viewer clicks badge → specmanager.org with UTM → GA records the visit; visit→install stays dark (accepted).

## 6. Failure & edge cases

- **Draft prototype blocking the Plan gate** — the headline failure mode. Without the `dependencies.ts` filter, every feature with a prototype could never open Plan (prototype status is frozen at draft). The selftest must cover this case explicitly.
- **Prototype shadowing the design card / stage label** — handled by the `findDoc` and `currentStageLabel` kind filters; `documents.ts` readdir order makes this real (mockups.html sorts before prototype.html, but don't rely on it).
- **No design doc yet** — `create_prototype` rejects when the feature has no non-prototype design-stage doc ("design is optional, therefore the prototype is doubly optional"). The UI shows no chip and no affordance until a design exists.
- **Oversized / malformed HTML** — 5MB cap reused; `---`-at-column-0 defanged by `sanitizeDesignBriefBody`; unparseable docs are already skipped-with-warning in `listDocuments` so a bad prototype can't take down the board.
- **Raw route abuse** — `/api/documents/:id/raw` serves only `.html` docs by id resolved through core (no path input), bound to `127.0.0.1` like the whole board.
- **Publish with missing/invalid token** — fail before any network call, with the two config locations in the message; no partial frontmatter writes.
- **Publish succeeds, frontmatter write fails** — order the stamp *after* a successful deploy; on stamp failure, surface the URL in the error so the user can unpublish manually; re-running publish unpublishes the orphan by `label`.
- **Unpublish when host unreachable** — keep `publishedUrl` in frontmatter and report failure; never pretend a public URL is gone.
- **Stale published URL** — `publishedVersion < version` renders an "out of date — republish for a new URL" state; republish mints a fresh URL and revokes the old.

## 7. Conventions used

- All mutations through `server/src/core/` — MCP tool and REST route are thin wrappers over the same functions; events via `core/events.ts`.
- Frontmatter authoritative, `manifest.json` rebuildable (manifest already round-trips `kind`).
- Non-lifecycle artifacts modeled as `kind` on `DocFrontmatterSchema`, status frozen at draft, excluded from gates/labels/primary cards — the interview precedent, followed exactly.
- Staleness via `dependsOn` graph + `propagateStale`; no parallel mechanism.
- Optimistic concurrency (`baseVersion`) on agent re-writes.
- zod schemas in `core/types.ts`; TS strict, ESM, Node 20+; latest `@modelcontextprotocol/sdk` / Fastify / React 18.
- Command→subagent delegation (`commands/*.md` → `agents/*.md`); persistence only via MCP tools, never `Write`.
- Secrets in `${CLAUDE_PLUGIN_DATA}`/env, never in the repo.
- Hand-rolled selftests in `server/src/selftest*.ts`; rebuild `dist/` before committing.

## 8. Open questions / risks

1. **Navigation wiring mechanism** in the generated HTML: pure CSS `:target` sections (zero JS, but no back-stack niceties) vs. a small inline `<script>` (richer flow, still self-contained). Recommend inline script; planner should fix this in the prototyper agent prompt.
2. **`findDoc`/label generalization scope:** change the filters from `kind !== "interview"` to `!d.kind` now (cheaper for future kinds) or add `"prototype"` literally? Recommend the generalization — `kind` is defined as "non-lifecycle" in `types.ts`.
3. **Concrete host for phase 2** (Netlify deploy API vs. Vercel vs. Cloudflare Pages): defer to the plan; `core/publish.ts` isolates the choice behind the contract in §4.
4. **Consent granularity:** per-publish confirm (recommended, matches "never a side effect") vs. per-feature remember-my-choice. PRD settles the requirement, not the mechanics.
5. **Should the chip also expose the prototype in `DocPanel`** (CodeMirror + iframe preview like the design brief) for inspection, or stay new-tab-only? New-tab-only is the PRD's ask; panel access is free if the chip routes through `onOpenDoc` secondarily.
6. **Badge UTM values** (`utm_source/medium/campaign`) need a final decision before phase 2 so GA dashboards are stable from the first publish.
7. **Demand risk (from the PRD):** zero observed shares to date; phase 2 is the experiment. Phase 1 must land and prove standalone value before any publish work starts.
