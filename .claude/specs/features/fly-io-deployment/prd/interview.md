*Builder / design-thinking mode — office-hours forcing questions (gstack method)*\n\n## Extracted\n\n- **Problem:** SpecManager's board and Claude Code session are locked to the dev machine. No way to view specs, approve docs, or trigger work from a phone or another device. The Claude mobile app gives generic Claude, not the project-aware Claude Code environment with plugins, MCP tools, and the specmanager workflow.\n- **Who:** The user and their teammates — everyone who needs to interact with the feature lifecycle.\n- **Core concept:** The board on Fly.io is the primary interface. Each feature has a chat panel that connects to a Claude Code session via `/resume`. The board is a second window into the same workflow, not a separate tool.\n- **Architecture — two-tier on Fly.io:**\n  - **Board server** — lightweight (512MB alpine), serves UI/API/WebSocket, always available or scale-to-zero\n  - **Claude Code runner** — heavier container, spun up on demand when work is triggered from the board, shuts down when idle\n- **Repo access:** Full repo clone on a Fly volume, git-synced. Claude Code runs against that clone.\n- **Push model:** Manual — Claude's changes stay on the Fly clone until the user reviews diffs on the board and explicitly triggers a push.\n- **Auth:** Shared bearer token for v1 (teammates get full access). Per-user identity deferred.\n- **Capabilities:** View specs, approve documents, inline comments + review (Claude rewrites based on comments), trigger Claude Code commands (build, PRD drafting, etc.), review diffs/commits, manual push.\n\n## Critique\n\n- **Session resume across machines is unproven.** `/resume` assumes conversation history in `~/.claude/` — syncing that between the terminal and the Fly instance is a hard problem not yet addressed. If the history lives only on the dev machine, the Fly instance can start *new* sessions but can't truly resume.\n- **On-demand Fly machines add orchestration complexity.** Spinning up and tearing down Claude Code runners means managing machine lifecycle, streaming output back to the board, and handling failures mid-run. This is significant infrastructure work.\n- **Full repo clone on a volume creates drift risk.** The Fly clone and the dev machine clone can diverge silently if git-sync isn't reliable. Manual push helps but doesn't prevent conflicts.\n- **\"Teammates can do all\" with a shared token means no audit trail.** You won't know who approved a doc or who triggered a build that broke something.\n- **Cost model is unclear.** On-demand Claude Code runners consume both Fly machine time and Anthropic API credits. With teammates all able to trigger builds, costs could spike unexpectedly.\n\n## Recommended wedge\n\nThe narrowest version worth building first:\n\n1. **Board server on Fly.io** — deploy the existing board (view specs, approve docs, track progress) with shared-token auth, full repo clone on a volume, periodic git pull\n2. **Inline comments + review** — add commenting to the board UI, \"Request Review\" sends comments to Claude via the existing agent-chat (uses `ANTHROPIC_API_KEY`, no Claude Code process needed)\n3. **Manual push from the board UI** — a button that pushes the Fly clone's commits to the remote\n\n**Cut from the wedge (deferred):**\n- Claude Code runner (on-demand Fly machines)\n- Shared/resumable sessions between terminal and board\n- Diff review surface\n- Per-user auth\n\n## Unresolved\n\n- How does session history sync between the dev machine and the Fly instance for `/resume` to work?\n- What Fly machine API or orchestration is used to spin up/down Claude Code runners on demand? Is `fly machines run` sufficient or does it need a queue?\n- What's the expected latency for git-sync? Is 5-minute polling acceptable or do teammates need near-instant visibility?\n- How does the board handle concurrent Claude Code runners (two teammates trigger builds simultaneously)?\n- What's the cost budget for Fly machines + Anthropic API usage?\n- Does the Claude Code runner container need the full plugin ecosystem installed, or just core Claude Code?
